# #178 异步回路排查与发布门禁（2026-10-24）

## 第二阶段结论（取代下文第一阶段的发布阻塞判断）

本轮通过名称读取兼容层切断三处控制器的 schemas 调用链：

- 官方主干已提供公开 definitions()，优先采用；但 npm 0.2.1-rc.2 和 0.2.1-rc.3 发布包尚未包含它。
- 对这些旧发布包采用只读、形状检查的 view() 兼容路径，仅读取 visible Map 的键，不读取参数、描述、输出或执行回调。此方法在旧宿主 typings 中是 private，属于明确承担的兼容依赖，不伪称公开 API。
- 验证环境包括本地真实 0.1.2-rc.1 和隔离安装的真实 0.2.1-rc.2。两种版本在 161 工具、12 个作用域的三种事件交付模式下，控制器 schemas 调用均为 0；轻量名称读取仍为同步 189 次、延迟 549 次，但不再做参数深克隆。
- 新增测试证明：一次外部 schemas 读取安排微任务通知后，控制器不再回调 schemas；真正新增的工具仍在三个限制层隐藏。
- 读取接口缺失或结构改变时不回退 schemas，不把读取失败当作空清单释放已有 restriction，执行 guard 保留；会话激活明确拒绝读取失败。
- 完整本地 check：454 项，446 通过、8 条件跳过、0 失败；90 个发布文件检查通过。三个 Host 集成测试已分别显式执行通过，不将普通 check 的 skip 计作通过。
- 新增 Windows/Linux × Host 0.2.1-rc.2/rc.3 的独立 CI，约束旧内部接口契约。PR 测试包依赖此门禁。

合并发布仍需最新提交全部 CI 通过。这里验收的是实际 Host 工具运行时和回路/权限机制，不是报告机器的 Desktop UI 或端到端 1.29 亿次调用对照；发布后 #178 应保留等待报告者复测，不能将目标机器体验宣称为已通过。

兼容层集中在 lib/host-tool-names.js。上游正式发布 definitions() 后自动优先使用公开接口；将来 view() 改动由合同测试和显式错误暴露，而非静默忽略工具变更。未修改用户 DSH 安装、profile 或凭据。

## 第一阶段结论（历史记录，已由上述第二阶段更新）

PR #179 是有效的扫描成本优化，但不是已验收的完整回路修复。保持 Draft，暂不合并、打 tag 或发布 npm；#178 保持开放。

## 环境与方法

- 本地：macOS arm64、Node v25.9.0；已安装 DSH / dsh-tools 0.1.2-rc.1。
- 报告：Windows 11、DSH Desktop 0.2.1-rc.2、插件 0.2.75。
- 测试文件：test/visibility-host.test.mjs。
- 使用实际 Cordis Context、ToolRuntime、createScope、schema 克隆和 restriction 生命周期。只替代 Agent 列表与 prompt 注册入口，不运行模型、UI 或真实用户 profile。
- 默认使用 Host 原生事件；另外两种模式仅在监听边界用 queueMicrotask / setImmediate 延迟交付，属于受控注入，不冒充 Host 默认行为。
- 161 个合成工具，其中 25 个管理工具名、136 个 MCP 工具名；12 个作用域。依次验证默认配置、三种限制共存、增加工具、删除工具、解除限制及释放资源。

运行时显式指定安装的 Host package.json：

```sh
DSH_HOST_INTEGRATION_ANCHOR=/absolute/path/to/dsh/package.json node --test test/visibility-host.test.mjs
```

未指定 Host 时测试明确 skip；指定后若依赖不兼容应失败。普通 CI 中 skip 不计入真实 Host 或 Windows Desktop 验收。

## 对照结果

旧版通过 git show v0.2.75 读取三处控制器，以内存 data URL 替换测试导入；未修改安装目录。仅取消旧版不应满足的“默认零扫描”断言，其余限制与生命周期检查保持一致。

| 事件交付 | 0.2.75 默认扫描 | PR 默认扫描 | 0.2.75 完整生命周期扫描 | PR 完整生命周期扫描 |
| --- | ---: | ---: | ---: | ---: |
| 原生同步 | 14 | 0 | 1078 | 189 |
| 微任务延迟 | 14 | 0 | 3094 | 549 |
| 下一轮 setImmediate | 14 | 0 | 3094 | 549 |

每种模式生命周期各收到 218 个真实注册/限制变更事件。三组均最终安静，不存在隐藏的后台持续扫描。工具新增后在受限作用域不可见，解除限制后恢复 161 个工具。

此外，原生 Host 中单独调用 schemas 不发送 tools/change；单次 restrict 的通知在返回前可观察到，等待微任务后没有额外通知。因此，不能从上述环境推出“restrict 的延迟通知自身必然造成无限循环”，也不能将报告中的 1.29 亿次 defineProperty 当作本次已复现的数值。

完整 check（显式启用 Host 集成）：449 项，445 通过、4 条件跳过、0 失败；89 个发布文件验证通过。这不覆盖 Windows Desktop UI。

## 未通过的回路边界

在独立合成 Host 中：

1. 配置一条 connection deny 规则，只有一个 Agent、一个 MCP 工具。
2. schemas 每次返回相同名称，但用 queueMicrotask 安排 tools/change。
3. restrict 不发送任何事件，排除 restriction 自身的影响。
4. 为防止测试饥饿，schemas 只在前 24 次读取中安排后续事件。

结果：共读取 25 次，恰好到达夹具通知上限才停止。说明相同名称/相同 deny 集合不会防止再次读取 schemas，布尔 syncing 对读取结束后的微任务无效。该实验定位残余机制，但不证明已安装 Host 原生 schemas 或某个真实第三方插件具有此副作用。

第一阶段只核对了本机 Host 的公开 schemas / get 接口，没有已验证可用的名称列表或 revision 接口。tools/change 无事件源及变更类型参数；其语义也包含 scoped restriction。当时未建立 view 的发布包兼容契约，因此没有直接调用它。第二阶段进一步核验官方主干和发布包后，采用了上述显式兼容层及版本门禁；仍不猜测事件来源、不永久缓存名称、不忽略后续变更。

## 下一步所需证据

- 事件发送栈：确认事件由注册/注销、restriction，还是其他插件在 schema 读取过程中触发。
