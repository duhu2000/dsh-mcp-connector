# 企查查旧 OAuth 插件迁移与恢复验收

日期为 2026-11-11。本文验证基于 v0.2.100 的工作区修复。已安装的原版 v0.2.100 不含本次指引。

## 客户从哪里处理

已经复制过旧授权的客户可以直接点市场卡片上的**连接异常**，或在**MCP连接器 → 已安装**选择该行的**查看处理步骤**。再次点击**检测企查查旧授权**也会列出尚待处理的迁移冲突。只处理弹框列出的插件或条目。

| 弹框中的情况 | 客户操作 |
| --- | --- |
| 旧插件仍启用 | 在 **DSH 主界面 → 插件 → 已安装** 按包名找到对应插件并关闭插件开关。旧版宿主可从设置里的插件市场进入。保留旧授权；旧插件的“断开”会尝试撤销刷新凭据。 |
| 旧插件本体已停用，旧服务条目仍启用 | 在宿主条目管理中核对弹框列出的完整 ID 和旧服务名，停用对应旧条目。宿主没有条目管理界面时，将这两项交给当前 profile 的管理员。法律条目的短 ID 可能与连接器共用。 |
| 已停用，等待重启 | 完全退出并重新启动 DSH，然后在 **MCP连接器 → 已安装** 检查对应服务。 |
| 需要重新授权 | 处理旧插件后，从市场中对应的卡片重新授权。旧授权失效时，仅重启无法恢复可用凭据。 |
| 仅内存模式 | 退出会清除本次复制的凭据。重启后再次检测并复制仍有效的旧授权，或从对应卡片重新授权。 |

## 两个旧插件的实际命名

下表是工商旧包 0.1.8、法律旧包 0.1.5 的默认名称。宿主可把插件本体放在 `include` 子树中。完整路径、旧客户端包名和配置中的 `serverName` 有助于辨别归属。

| 服务举例 | 旧插件 ID / 安装包 | 旧条目短 ID / 旧 serverName | 新条目短 ID / 新 serverName |
| --- | --- | --- | --- |
| 企业工商 | `qcc-mcp-oauth` / `qcc-dsh-mcp-oauth` | `mcp-qcc-company` / `company` | `mcp-qcc-company-company` / `qcc-company` |
| 法规 | `qcc-legal-mcp-oauth` / `qcc-dsh-mcp-legal-oauth` | `mcp-qcc-legal-regulation` / `legal-regulation` | `mcp-qcc-legal-regulation` / `qcc-regulation` |
| 案例 | 同上 | `mcp-qcc-legal-case` / `legal-case` | `mcp-qcc-legal-case` / `qcc-case` |

原问题中工商 6 条记录保存了旧插件冲突提示，法律 2 条未保存错误。截图可以说明卡片状态。识别迁移冲突要查看宿主条目及授权归属；默认工商服务的新旧注册名实际不同。此前使用模拟插件的验收在重启前手工移除了残留，只证明了无残留时能恢复。

## 回归用例

| 场景 | 验收结果应满足 |
| --- | --- |
| 两个旧插件启用，或只启用其中一个 | 只复制已授权资源。报告正确的插件、安装包和受影响服务。旧授权原样保留，冲突期间不新建或覆盖宿主条目。只有案例授权的客户不应收到法规条目的处理指令。 |
| 已迁移、已关闭弹框、刷新页面或再次扫描 | 市场红卡一击打开当前连接的处理步骤。已安装行可打开同一指引。零个待复制授权时仍可查看冲突。英语界面显示相应英文。 |
| 远端可用、工具列表有旧缓存或详情请求迟到 | 冲突优先显示。点击异常不会把卡片变成“已连接”，也不会发起针对被阻断连接的工具发现。 |
| 从已安装开关、重新连接、启动恢复或快照重建 | 旧插件持有服务期间无法注册冲突条目；法律旧条目的配置、启停状态与凭据保留。 |
| 停用本体但留下法律旧条目 | 显示“残留条目”和实际完整 ID。区分 `legal-case` 与 `qcc-case`。清除冲突后，连接器创建的同 ID 条目不会被当作旧残留。 |
| 旧插件最后一次轮换刷新令牌 | 等待接管期间连接器不刷新同一授权。停用并重启后读取对应旧来源的最终授权；已经由连接器轮换的新凭据不会被旧副本覆盖。 |
| 失效授权、旧版自动停用的迁移记录、仅内存 | 客户看到重新授权或重启后再次复制的操作。检查手动停用的连接不会被自动启用。 |
| 交接时旧授权存储损坏或不可读 | 保留待交接状态，指引管理员检查存储。连接器不使用可能过时的副本注册或刷新。 |
| 处理完成 | 实际宿主中注册新工具，连接状态恢复，处理指引消失；另一插件仍有冲突时可以单独处理。 |

## 在隔离环境重跑

在源码仓库根目录用 Node 22 执行常规测试。测试使用合成授权和本机模拟服务。

```sh
node --test test/legacy-plugin-conflict.test.mjs test/ui-legacy-migration.test.mjs test/plugin-flow.test.mjs
npm run check
```

真实宿主专项测试会创建一个临时 `DSH_HOME`，把两个已安装旧包的**程序目录**和工作区连接器链接到临时 profile。测试使用临时授权、环回 MCP 服务、真实 DSH loader 和无头 Chromium，结束后关闭服务并清理临时 profile。原有 profile、存储和桌面进程均不需要操作。

先安装可用于该 DSH 版本的 Node、Playwright 及其 Chromium，并指向本机现有的程序目录。PowerShell 示例：

```powershell
$env:DSH_LEGACY_TEST_CLI = '<DSH 程序目录>/lib/bin.js'
$env:DSH_LEGACY_TEST_MODULES = '<包含两个旧插件安装包的 node_modules>'
$env:PLAYWRIGHT_MODULE = '<playwright 或 playwright-core 的程序目录>'
node --test test/legacy-migration-dsh.test.mjs
```

指定 `DSH_LEGACY_TEST_CLI` 会启用真实宿主验收；程序包或浏览器不可用时会报错。需要使用指定的 Chromium 时可以设置 `CHROMIUM_EXECUTABLE`。

## 本次隔离验收记录

Windows 上使用 DSH CLI 0.2.2-rc.1、工商旧包 0.1.8、法律旧包 0.1.5。三个进程先后启动同一临时 profile。以下步骤已实际通过。

Node 22.22.1 的 `npm run check` 通过，640 项测试中 631 项通过、9 项跳过、0 项失败。默认跳过的真实双插件宿主专项另行启用并运行。发布包白名单和教程链接检查均通过。

| 启动与操作 | 观察结果 |
| --- | --- |
| 两个旧插件启用，复制工商和案例授权后打开新的 Chromium 页面 | 两张“连接异常”卡片各自一击显示准确的旧安装包和插件 ID。“已安装”法律行只显示法律指引；再次扫描在零个待复制授权时仍列出两项。尝试重连被阻止，Host 里只有旧工具名。 |
| 旧法律来源在临时存储中模拟最后一次轮换，停用两个旧插件，保留一条启用的旧法律服务 | 工商恢复。法律诊断为残留条目，给出 `mcp-qcc-legal-case` 的完整路径；连接器未接管该活动条目。 |
| 将上述法律旧条目标记为停用，保留其配置，完整重启 | 两条连接的工具发现均健康。法律 mock 只接受最后轮换的合成凭据；宿主工具注册表中实际出现 `mcp__qcc-company__echo_company` 与 `mcp__qcc-case__echo_case`。 |

## 本机 Web 宿主实测

在 DSH Web 0.2.2-rc.1 的现有 `web` profile 中，使用内置浏览器验证了已迁移客户的恢复流程。两个旧包都已安装并启用。原版 0.2.100 的工商红卡会打开普通详情，只出现“重新检查”和“断开连接”，法律卡片当时显示“已连接”。

| 实际操作 | 实际观察 |
| --- | --- |
| 备份原版程序文件，安装工作区修复，从原 PowerShell 重启 DSH 以加载修复 | 工商和法律各自出现“连接异常”。逐一点击后，工商弹框列出 `qcc-mcp-oauth` 和安装包 `qcc-dsh-mcp-oauth`，法律弹框列出 `qcc-legal-mcp-oauth` 和安装包 `qcc-dsh-mcp-legal-oauth`。 |
| 在 **DSH → 插件 → 已安装** 关闭上述两个安装包的开关，再次点击红卡 | 两个旧开关均已关闭，连接器仍启用。两张卡片分别提示工商 6 项、法律 2 项等待重启。本次没有残留条目需要手工处理。 |
| 在原 PowerShell 完整重启 DSH，打开 **MCP连接器 → 已安装** | 原来的 17 条连接仍在。工商的 company、risk、ipr、operation、history、executive 和法律的 regulation、case 全部显示“已连接”，每条的可用性检查均为 `ok`。 |
| 打开市场中的工商和法律详情 | 工商工具目录显示 6 个服务、356 个工具，法律显示 2 个服务、10 个工具。整个恢复过程沿用已迁移授权，无需重新登录企查查。 |

本次第一次重启用于加载本地补丁。已运行修复版的客户从红卡开始，在停用旧插件后重启。本次验证使用已授权账户和工具目录，没有执行具体企业或法律业务查询。

## 验证边界

上述实机结果适用于该版本的 Web 宿主。全新账号的 OAuth 登录、桌面壳的原生插件开关、剪贴板权限和其他宿主版本的导航仍待验证。
